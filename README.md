# F&B Pilot — 매장 입고·발주·매출 예측 도우미

F&B 매장 관리자가 매일 아침 "오늘 무엇을 발주해야 하나, 재고는 언제 떨어지나, 이번 주 매출은 어떤가"를 한 화면에서 보고 판단하도록 돕는 프로그램입니다. 실제 F&B 현장에서 근무하며 엑셀과 수기로 재고·발주를 계산하던 경험에서 출발했습니다. 관리자를 대신하는 AI가 아니라, 경험과 감각으로 하던 판단을 데이터가 보조하는 것이 목표입니다.

- **주요 사용자:** F&B 점주, 매장 관리자, 슈퍼바이저 (현재는 수원점 1개 매장 데이터로 만들었습니다)
- **해결하려는 문제:** 실사 재고 단위 환산, 거래처별 발주 요일·리드타임, 휴점일, 최근 매출을 사람이 매번 직접 계산하는 일
- **데이터 범위:** 매출(POS)과 월별 수불부는 2024년 1월~2026년 9월까지이고, **2026년 9월 데이터 이후로는 데이터가 없습니다.** 구매청구·입고 리스트만 2026년 10월 1~24일분이 있습니다. 2026년 10월 이후 재고는 예측값입니다.
- **저장소:** 비공개. 실제 매장의 POS·수불부 정제 데이터가 들어 있습니다.

## 무엇을 하나

| 기능 | 내용 | 상태 |
|---|---|---|
| 일 매출 예측 | 같은 요일 최근 중앙값 × 전년 계절 보정, 공휴일·징검다리 평일 배율, P10~P90 범위 | 구현 |
| 발주 시점·수량 추천 (발주 엔진) | 품목별 발주 확률(주기·경과일·요일 습관)과 평소 주문량 | 구현 |
| 재고·입고 순환 시뮬레이션 | 마지막 월말 실사에서 출발해 날마다 재고 = 어제 − 소비 + 입고, 발주일 예측 | 구현 |
| 단위 환산 | kg / BOX / PK / EA / g 변환, 발주단위로 수량 표시 | 구현 |
| 실사 재고 파일 업로드 | xlsx·csv·json·마크다운 표·메모 형식 | 구현 |
| F&B Agent 챗봇 | 키워드 규칙 기반 (LLM 아님) | 부분 구현 |
| 유통기한·위생, 인건비·스케줄 연동, 매뉴얼 RAG | 기획 단계 | **미구현** |

## 실행 방법

```bash
cd fb_agent
python -m venv venv && source venv/bin/activate
pip install -r requirements.txt
./run_real.sh            # 또는 FB_MASTER=real streamlit run app.py
```

브라우저에서 `http://localhost:8501`을 엽니다. `data/real/`에 실제 데이터 기반 마스터(품목 811개·거래처)가 들어 있어 별도 준비 없이 실제 데이터로 뜹니다. 근거가 없는 값은 가상으로 채우지 않고 `데이터 없음`으로 표시합니다.

```bash
python -m unittest discover -p "test_*.py"     # 단위·화면(AppTest) 테스트 389개, 약 80초
python inventory_sim.py --backtest             # 재고·입고 시뮬레이션 백테스트 (2025-07 이후 매월 출발)
python inventory_sim.py --verify 2026-10       # 동결한 예측과 실제 수불부 비교 (2026년 10월 수불부가 있을 때)
python reorder_engine.py --fit 시작 끝          # 발주 확률 모델 재학습
```

데이터 정제는 `python -m prep ...`, 마스터 재생성은 `python -m prep.app_master`입니다. 자세한 내용은 [fb_agent/README.md](fb_agent/README.md)와 `fb_agent/docs/`를 참고하세요.

## 작업 과정

1. **화면 뼈대:** 메뉴 56개, 달력 대시보드, 우측 에이전트 패널을 Streamlit으로 먼저 만들었습니다.
2. **실제 데이터로 교체:** 처음에는 가상 값(리드타임·재고·소비량)이 섞여 있었습니다. 수원점 POS(2024-01~2026-09), 월별 수불부 21개월, 구매청구·입고 리스트를 정제해 연결하고, 가상 값은 모두 지우고 근거 없는 값은 `데이터 없음`으로 바꿨습니다.
3. **예측 엔진:** 매출 예측 → 발주 엔진 → 재고·입고 시뮬레이션 순으로 쌓았습니다. 새 방법은 먼저 기준선과 백테스트로 견주고, 이기는 것만 화면에 연결했습니다.
4. **현장 규칙 반영:** 백화점 고정 휴점, 공휴일·징검다리 평일, 업체별 입고 요일(일요일 입고는 CK뿐), 안전재고 기준을 실측으로 보정했습니다.
5. **예측 동결과 검증:** 2026년 9월 말 실사에서 출발한 2026년 10~12월 예측을 `data/forecast/2026-09_출발/`에 동결해 두고, 이후 들어온 2026년 10월 구매청구·입고 리스트로 채점했습니다.

작업은 Claude Code와 함께 했고, 기능마다 브랜치를 만들어 커밋한 뒤 `main`에 머지했습니다.

## 검증 결과와 작업 증거

모든 수치는 예측을 만들 때 쓰지 않은 기간·자료로 잰 값입니다.

| 대상 | 방법 | 결과 | 비교 기준 |
|---|---|---|---|
| 발주 시점 | 2025-07~12 학습, 2026-01~09 검증 | F1 77.1%, AUC 0.82 | 간격 규칙 69.7%, 전부 발주 66.2% |
| 발주 수량 | 같은 기간 | WAPE 31.1% | 평소 주문량 그대로 32.3% |
| 월말 재고 | 시뮬레이션, 2025-07~2026-08 출발 백테스트 | WAPE 31% | 출발 재고 그대로 37% |
| 월 입고 / 월 소비 | 같은 백테스트 | WAPE 24% / 21% | 최근 3개월 평균 28% (입고) |
| 2026년 10월 발주일 | 동결 예측 vs 2026년 10월 1~24일 구매청구 | ±1일 정밀도 76%, 재현율 83% | '4주 전 반복' 기준선과 거의 같음 |
| 2026년 10월 입고량 | 같은 비교 | WAPE 31% | 기준선 34% |
| 평일 매출 | 2026년 | 오차 약 21% | — |

**버린 방법도 기록했습니다.** 수요×소비율로 수량을 계산하는 방법(오차 43%), 재고 추정만으로 발주 시점을 판단하는 방법(F1 58%, 기준선보다 나쁨), 발주 엔진을 시뮬레이션의 입고 생성기로 쓰는 방법(오차 70~200%)은 기준선보다 나빠서 쓰지 않았습니다.

**최근 개선 사례:** 시뮬레이션이 쓰지 않는 품목을 쓴다고 보던 문제를 백테스트로 확인했습니다. 출발일 45일 안에 입고가 없으면 제외하는 기준을 넣었더니 잘못 본 품목이 67개에서 41개로 줄었고 입고 WAPE는 29.2%에서 28.6%로 약간 좋아졌습니다. 효과가 작다는 점도 그대로 적어 두었습니다.

**두 가지 보정을 더 넣었습니다.** 평소 재고 수준을 '처음 쓰기 시작한 달'부터 계산하고(새 품목의 0이 기준을 끌어내리던 문제), 출발 직전 달 소비가 0인 품목은 소비 0으로 봅니다(끝난 시즌 품목). 월 입고 WAPE는 24.4%에서 23.8%로, 월말 재고는 30.4%에서 약 29.8%로 좋아졌습니다. 기간·요일 기준 등 다른 모수 11가지는 이미 최적에 가까워 바꾸지 않았습니다.

- 자동 테스트 389개 통과 (`test_inventory_sim.py`, `test_reorder_engine.py`, `test_sales_forecast.py`, `test_stock_sim.py` 등)
- 커밋 이력: `git log`의 기능별 브랜치 머지 (`feat/inventory-sim`, `feat/order-plan`, `fix/urgent-items`, `feat/oct-po-data` 등)
- 동결 예측과 검증 CSV: `fb_agent/data/forecast/`
- 방법·수치 문서: `fb_agent/docs/INVENTORY_SIM.md`, `DATA_CLEANING.md`, `LEDGER_RECONCILE.md`

## 효과적이었던 실천 방법 3가지

1. **기준선과 백테스트를 먼저 놓고 채택 여부를 정했습니다.** 그럴듯해 보이는 방법도 단순 기준선을 못 이기면 버렸습니다. 어떤 방법이 왜 졌는지까지 남겨서 같은 시도를 반복하지 않았습니다.
2. **예측을 동결하고 나중에 채점했습니다.** 같은 이름으로 다시 만들면 거부되게 해서, 결과를 본 뒤 모수를 고치는 일을 막았습니다.
3. **실제 값만 쓰는 원칙과 현장 지식을 규칙으로 옮겼습니다.** 가상 값을 지우고 `데이터 없음`으로 표시했고, 사용자가 짚어 준 현장 사실(일요일 입고는 CK뿐, 공휴일 효과, 휴점일)은 데이터로 확인한 뒤 코드와 CSV에 반영했습니다.

## 어려웠던 점 3가지

1. **재고 데이터가 월말 실사뿐이고 2026년 9월 이후로는 없습니다.** 하루 단위 재고를 직접 관측할 수 없어서 소비와 입고를 모델로 굴려야 했고, 품목별 월말 재고 오차는 입고가 몰려 들어오는 주기 때문에 줄이기 어려웠습니다.
2. **자료마다 단위와 기준이 달랐습니다.** 구매청구(발주단위), 수불부 입고(규격 단위), POS(금액)를 맞추고 21개월 수불부를 정제·대조하는 작업이 컸습니다.
3. **불규칙한 품목이 많았습니다.** 시즌 메뉴 품목, 몇 달에 한 번 사는 품목, 직원 중식 때문에 폐기량이 흔들리는 품목은 "쓰는 품목인가"부터 판단하기 어려웠습니다. 휴면 판정을 엄격하게 하면 필요한 품목을 놓치고 느슨하게 하면 없는 입고를 예측했습니다.

## 알려진 한계점

- **기능 범위:** 기획한 3대 기능 중 재고·발주 분석이 중심이고, 유통기한·위생·인건비 연동과 매뉴얼 RAG 질의응답은 구현하지 못했습니다. F&B Agent는 LLM이 아니라 키워드 규칙 기반입니다.
- **한 매장 데이터:** 수원점 하나로 만들고 검증했습니다. 다른 매장이나 업종에서의 정확도는 모릅니다.
- **예측 정확도:** 품목별 월말 재고 WAPE 약 31%, 입고량 약 31%입니다. 발주일 예측은 '4주 전 반복' 기준선보다 낫다고 말할 수 없습니다. 평일 매출 오차는 20% 안팎의 일상 변동이라 범위(P10~P90)로 보여 줍니다.
- **2026년 10월 이후는 예측입니다.** 2026년 9월 데이터 이후로는 데이터가 없고 실사 재고를 더 올리지 않는 전제라, 2026년 9월 말 이후 재고는 시뮬레이션 값입니다. 2026년 10월 수불부로 하는 전체 월 검증은 아직 하지 못했습니다(2026년 10월 1~24일 구매청구·입고만 검증).
- **휴면·시즌 품목:** 입고가 45일 넘게 없던 시즌 품목은 입고가 생긴 뒤 마스터를 다시 만들어야 살아납니다.
- **인증·저장:** 로그인은 비밀번호 없는 데모이고, 일정은 세션에만 저장됩니다.
- **원본에 없는 값:** 회전율(좌석 수), 결제채널 수수료, 취소 사유는 제공하지 않습니다.
